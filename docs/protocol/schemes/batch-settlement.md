# batch-settlement (payment channels)

For prices too small to settle one transaction per request. The payer escrows funds once in a `blockpay::channel::Channel<T>`; each request is paid with an off-chain **voucher**: a signature over the running total. The facilitator verifies vouchers in milliseconds and redeems the latest one on-chain in batches.

This page is BlockPay's Sui binding of the x402 [`batch-settlement`](https://github.com/x402-foundation/x402/blob/main/specs/schemes/batch-settlement/scheme_batch_settlement.md) scheme (capital-backed model). It will be proposed upstream once it has run in production.

### Requirements `extra`

| Field | Description |
| --- | --- |
| `operator` | Facilitator address. May cooperatively close the channel; receives no funds. |
| `channelPackage`, `channelRegistry` | The `blockpay::channel` deployment. **Clients must check these against their own trusted configuration**, never trust them from the 402 alone. |
| `withdrawDelayMs` | Minimum delay between the payer's `request_close` and `withdraw`. 15 minutes to 30 days. |
| `minDeposit` | Suggested deposit when opening, atomic units. Clients cap deposits locally. |
| `feePayer` | Optional sponsor for open / top-up transactions. |

### Payloads

```jsonc
// First request: open the channel and pay
{ "type": "open", "transaction": "<base64>", "transactionSignature": "<base64>",
  "channelId": "0x…", "cumulativeAmount": "1000", "signature": "<base64 ed25519>" }

// Following requests: voucher only
{ "type": "voucher", "channelId": "0x…", "cumulativeAmount": "2000", "signature": "<base64>" }

// Deposit exhausted: top up and pay
{ "type": "topUp", "transaction": "<base64>", "transactionSignature": "<base64>",
  "channelId": "0x…", "cumulativeAmount": "6000", "signature": "<base64>" }
```

### Voucher

```
message   = "blockpay/channel/voucher/v1" || bcs(channel_id: 32 bytes) || bcs(cumulative: u64 LE)
signature = Ed25519(authorizer_secret, message)       // 64 bytes, raw message (no intent prefix)
```

The `authorizer` is a fresh Ed25519 key per channel, generated by the client and recorded in the channel at open. It can only pay that channel's `payee`, up to the deposit: an on-chain spending limit for agents.

### Channel IDs are known in advance

Channels are created with `sui::derived_object` from the registry and `ChannelKey { payer, nonce }`. The client computes the ID before the open transaction runs, so the first request can carry both the open transaction and a voucher. A derived ID is never reused, even after the channel is deleted, so vouchers cannot be replayed against a later channel.

### Verification (facilitator)

* **voucher** — the channel exists and is open; `payee == payTo`, coin type `== asset`, `operator ==` this facilitator; `cumulative ≥ watermark + amount`; `cumulative ≤ deposited`; the signature verifies against the channel's authorizer. Channel state is re-read from chain at least every 30 seconds so payer exits are noticed.
* **open / topUp** — transaction signature and sponsor policy as for `exact` (only `channel::open` / `channel::top_up` and coin operations may be sponsored), then simulation; the emitted `ChannelOpened` / `ChannelToppedUp` event must match the channel ID, payee, operator, asset and withdraw delay; then the voucher check against the event's data.

### Settlement

* **open / topUp** — execute the transaction (co-signing if sponsored), wait until it is checkpointed, record the channel.
* All types — atomically raise the channel watermark to `cumulative` (compare-and-set). The response's `transaction` is the commitment `<channelId>:<cumulativeAmount>`; for open/top-up, `extensions.sui.fundingTransaction` holds the digest.

Clients keep one voucher in flight per channel so cumulative amounts arrive in order. For parallelism, open several channels.

### Redemption

The facilitator's redeemer calls `claim(channel, cumulative, signature)` for every channel with unredeemed value — many channels per transaction — on a schedule (default: every 60 s; vouchers older than 5 minutes are always redeemed). `claim` is permissionless and always pays `payee`, so a merchant can also redeem the latest voucher (shown in the dashboard) without the facilitator.

### Closing

| Path | Who | Effect |
| --- | --- | --- |
| `claim` + `close` | payee or operator | Redeem the final voucher, refund the rest to the payer, delete the channel. The redeemer can do this for idle channels. |
| `request_close` → wait `withdraw_delay` → `withdraw` | payer | Unilateral exit. The payee can still `claim` during the delay. |

### Trust model

* The payer's risk is bounded by the deposit, and the payer can always exit.
* The merchant's risk is unredeemed value: accepted vouchers not yet claimed. Keep the redemption interval well below the withdraw delay (the default is 5 minutes against a 15-minute minimum).
* The facilitator cannot redirect funds. As `operator` it could close a channel before claiming the latest voucher; the funds then return to the payer, not to the facilitator.
